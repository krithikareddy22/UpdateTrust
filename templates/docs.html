A concise guide to the cryptographic design and the key security decision in UpdateTrust.

Problem statement

Software update packages may be modified, replaced by an untrusted source, or downgraded to an older vulnerable version. Hash checks alone do not prove who created a release, and signatures alone do not stop an older signed package from being replayed.

Objectives

  • Use SHA-256 to detect package modification.
  • Use Ed25519 signatures to authenticate release metadata.
  • Check publisher trust independently.
  • Remember the highest accepted version per product.
  • Reject rollback and same-version replay attempts.
  • Keep uploaded packages inert and never execute them.

Core verification logic

  1. Load release and publisher record.
  2. Recompute package SHA-256 and compare it to the manifest.
  3. Reject untrusted publisher identities.
  4. Verify Ed25519 signature over canonical manifest bytes.
  5. Within a write transaction, compare release version to trusted version.
  6. Accept only a strictly newer version and atomically update state.
Key takeaway

Rollback prevention requires persistent trusted state. A signature proves origin/integrity of signed data, not that the release is the newest one.
